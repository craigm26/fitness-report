Fitness Report

Methods, and the record of what went wrong.

26 entries in the failure record. 6 are open today.

This product's entire claim is that it refuses to publish numbers it cannot support. A claim like that is worth nothing unless the failures are published to the same standard as the findings, so they are, on this page: what broke, what it would have caused, how it was caught, and the evidence you can go read yourself.

Conformance asks whether the server speaks MCP correctly. Fitness Report asks whether an agent can actually get the job done with it.

That first word belongs to the official suite at github.com/modelcontextprotocol/conformance. It is a different project answering a different question, and nothing on this site is a substitute for it. Run both.

What one scored run reports

A run drives one server version with one runner model against a task suite generated for that server's own tool surface. Every task is machine checked. What comes out is a small, fixed set of numbers, each of which is either a finite value or absent from the record entirely. There is no NaN here, and no zero standing in for something unknown.

  • First-try success, as a count and a Wilson 95% interval. The interval is the finding. The point estimate is drawn inside it and is not the result.
  • Eventual success, the same task set counted after retries, so the gap between the two is the cost of the server's first answer being wrong.
  • Calls, tokens and dollars per completed task, netted of the fixed tool definition overhead for the runner model.
  • Per-tool failure attribution, by class: protocol error, execution error the agent recovered from, fatal execution error, abandoned after too many clarification rounds, and schema validation reject. The last of those is always a finding about the server and is never attributed to the agent.
  • Destructive calls with no confirmation in front of them. A tool is treated as destructive unless it declares otherwise, because that is the spec default, and a confirmation only clears a call when it names the same tool and lands before the call executes.
  • Declared against inferred destructiveness, where the two disagree.
  • Ambiguous parameter names, schema drift, and the tool surface delta by credential where a second credential was available.
  • Deterministic protocol probes, which cost zero tokens and run before anything else, so even a refused run reports them.
  • Credential context, stamped on every number: anonymous, free key or owner key.

Every one of those fields is in data/runs.json for every published run, alongside the two tapes the numbers were read from. Nothing on the board is stored anywhere else.

What it refuses to measure

Whether the server is correct
Protocol probes are reported, and a failed probe is coloured as a fact about the server, but this harness does not certify a server against the specification. The official suite does that.
Which model is better at using tools
The runner model is pinned into every score record and held constant inside a comparison. This board is about servers.
Anything at all, when the eval itself is invalid
When a validity gate fails, the report carries no score field. Not null, not zero: absent. The refusal is published in the slot a number would have occupied, with the failing gate, its counts, its threshold, its alpha, its p-value and its reason string.
A ranking
No row on the board sits above another. At these sample sizes the intervals overlap, and an order between overlapping intervals is decoration.
A dollar figure it cannot support
An unpriced model produces no number rather than a wrong one, and a figure known to be incomplete is published as a floor and says why. See cost honesty.

2. The gates, in cost order

Cheapest first, stopping at the first failure, so a broken eval never spends model budget.

The gate names, cost tiers and order below are the ones written into every run record, in the record's own words. You can read the whole ladder for any published run in data/runs.json under gates.order and gates.records. Each rung says what it checks, what running it costs, and the thing that matters most: whether a failure there is a statement about the server or a statement about our own measurement.

  1. protocol_hygiene free / zero tokens

    Deterministic protocol probes

    Checks

    The revision the connection actually negotiated, whether the server accepts an impossible protocol version, whether a mismatched method or name header is rejected, whether the modern server discovery method is implemented, whether cache hints are present and correctly scoped, and the deprecation surface. A probe that does not apply to a connection is reported as unknown and never folded into the pass count.

    Costs

    Pure transport. No model is called, so this runs even on servers that will refuse everything afterwards.

    A failure here means

    Server. This gate is a reported column, never a refusal. The record says so in its own note: a hygiene failure is a fact about the server, not evidence that the eval is invalid. Five of the seven scored rows on the board carry a hygiene finding and are scored anyway.

  2. structural free / zero tokens

    Did the generator produce a usable suite

    Checks

    How many candidates the generator emitted, how many survived admission, the admission rate against a floor of 0.25, and an absolute minimum of 8 admitted candidates. Every rejection is counted under the rule that produced it, and those counts are published on the row. The per candidate ledger behind them is written to the run's suite metadata file, which is not published; entry 17 is what that costs.

    Costs

    Nothing. It reads the generator's own ledger.

    A failure here means

    The eval. Reason no_cases_generated means our generator admitted nothing. It is not a statement about the server, and entry 03 in the failure record is what happens when that distinction is not made loudly enough on the board.

  3. answer_leak free / zero tokens

    Does a task carry its own answer

    Checks

    The rendered prompt, with parameters bound from the wire, against the answer the check expects. A leak found at generation time buys exactly one regeneration attempt; a leak still present after that refuses the run.

    Costs

    A string scan. The one regeneration attempt costs a judge call.

    A failure here means

    The eval. A task that contains its answer measures nothing about the server. This gate was blind for the entire first pass: entry 04.

  4. suite_size free / zero tokens

    Is there enough surface to say anything

    Checks

    Admitted tasks against a hard minimum of 8. The open server roster has a median of about two and a half tools, so this fires often.

    Costs

    Nothing.

    A failure here means

    The eval. It publishes as INSUFFICIENT_SURFACE, which is a refusal to score, not a verdict. A two-task suite at 100% is a worse outcome than an honest refusal, so this floor does not move.

  5. plan_power free / zero tokens

    Is this sample big enough to resolve the question

    Checks

    The registered n against the sample size planned for the threshold and the detectable rate, and the achieved power at the run's own n. Exact binomial power is sawtoothed in n, so clearing the planned size is not the same claim as being powered at it.

    Costs

    Nothing. It is arithmetic on the registered plan.

    A failure here means

    The eval. Recorded as underpowered_recorded rather than hidden, and carried into the published-pass rule in divergence 2.

  6. null_baseline cheap / three passes over the suite

    Could a model pass this without the server

    Checks

    Three null models run the same suite: one with no tools at all, one whose tool calls come back empty, and one calling tools with random valid arguments. The highest of the three is the noise floor. If it reaches half the real signal or more, the suite is killed. An indeterminate result halts exactly like a kill.

    Costs

    Three passes over the suite at the runner model. Measured before any paid call: every published record carries measuredBeforePaidTier: true. It is decided later, because deciding needs a real signal to compare against, and the record names which signal it used in decidedAfter and signalSource.

    A failure here means

    The eval. When a model with no tools passes most of the suite, our tasks were answerable from what the model already knew. It publishes as DEGENERATE. Seven of the first pass's rows died here, and entry 02 is the honest reading of what those seven rows were actually about.

  7. construct paid / one reference pass per task per rep

    Can the answer be reached at all, through this server

    Checks

    A reference agent is handed the answer key and must still reach it, at a rate of at least 0.90, through the server. Reaching it is not enough on its own. The run also has to show a successful tool call to an expected tool, because a substring or regex check on final text can be satisfied with zero tool calls against a dead server.

    Costs

    The first paid tier. One reference pass per task per registered rep, at the runner model, plus the judge spend already sunk into generating the suite. Across the 13 published runs that record judge usage, that synthesis cost ran from $0.2642 to $1.4495.

    A failure here means

    Both are possible, and the record distinguishes them. When the reference pass never reached the server, the record reads the tape and prints the counts: tool calls recorded, calls that came back as errors, and requests that never received a matching protocol response. A server that advertises tools and then rejects every invocation is a finding about the server, stated from those counts and never assumed. Anything else is a statement about our suite.

  8. the drive paid / the full run

    The measurement itself

    Checks

    Nothing. Every gate has already passed. This is the scored agent loop, recorded to two tapes: the MCP wire plane and the agent plane.

    Costs

    The bulk of the run. Every task carries a task budget, so a server that traps the agent yields a clean unrecoverable-path datum instead of an unbounded bill.

    A failure here means

    Server. By this point the eval has been cleared four different ways, so a task that fails on the drive is the measurement, not an error.

3. Two divergences from evalgate

The gate math is ported. It differs in exactly two places, and both are ours to defend.

  1. Construct errors count in the denominator

    evalgate shrinks the denominator when an oracle call throws. Three successes out of three completed calls then reads as a perfect rate even when forty calls errored on the way, because the forty were never counted. That is defensible for a local oracle and wrong for a flaky remote server, which is every server on this board.

    Here the errors are gated on their own: errors / (n + errors) > 0.05 resolves the run to COMPROMISED. That is not a verdict about the server. It is a refusal to score, because the measurement did not complete. The variance gate was also changed to catch oracle exceptions, which evalgate's does not, and the structural gate was given a minimum admission rate and a minimum absolute n, because evalgate passes on five generated cases out of two hundred.

  2. A published pass is symmetric with a published failure

    A pass on the board additionally requires that the Wilson 95% lower bound sits at or above the threshold, or that the run's own n achieves the planned power against the detectable rate. Otherwise the verdict is downgraded to EXTEND and no pass is published.

    The reason is symmetry, not caution. Failures on this board are published at full statistical rigour, and a small sample that happens to land above the line is not evidence. Publishing the lucky one while holding the unlucky one to a p-value would put a thumb on the scale in exactly one direction. Because exact binomial power is sawtoothed in n, the test is run against the run's actual n rather than against the planned size it cleared.

4. The extension protocol

Fixed in code, reachable by no flag, because a budget that can be raised mid-run is optional stopping.

Size
6 new tasks per extension.
Maximum
2 extensions per run.
Generation
The same generator at a derived seed, put through the same free gates and measured by the same three null baselines as the registered suite, and run at the same reps.
Pooling
Successes and trials are pooled across the registered suite and every consumed extension, and the three-outcome rule is re-applied to the pooled counts. Nothing is re-tested in isolation.
Resolution
After the last extension, a gate that is still unresolved resolves to FAIL, and the run refuses as GATE_FAILED.

The policy is registered into the run record before the first model call, so you can read what a run had bought before it knew anything. In the source it is a frozen constant, EXTENSION_POLICY = Object.freeze({ extensionSize: 6, maxExtensions: 2 }), and no flag, option or environment variable reaches it. That is deliberate and it is the whole point: an extension budget an operator could raise after seeing a verdict is optional stopping wearing a constant's name. There is no path in this codebase that lets a run buy its way to a decisive number.

A regenerated task suite is a new run under a new suite hash, never a retry of this one. Reruns are published as separate attempts and an earlier run is never replaced or hidden, whatever its outcome was.

Verify: src/cli.ts lines 98 to 123 for the constant and the doctrine comment, lines 156 to 200 for the full flag list, which contains no extension flag, and gates.extensionPolicy on every row of data/runs.json.

5. The failure record

Twenty-six entries covering this harness and the tooling under it: what broke, what nearly broke, and what is still open.

Negative results and invalid environments are usually discarded, so every team pays to rediscover them. That is the argument behind the operator's earlier FOIL project, which published its kills, its gate failures, a retracted claim and its invalid environments as importable fixtures. This page holds Fitness Report to the same standard, for a reason specific to this product: a harness whose selling point is refusing to publish unsupported numbers has no business hiding the times it published one anyway, or nearly did.

How to read a status

  • OPEN Still true today.
  • CLOSED Was true, is fixed, and the fix is pinned by a test.
  • CAUGHT EARLY Found and closed before any published file or number carried it.
  • ON RECORD A published fact or event that stands as published.

How to read the evidence

This repository is public, so a commit hash or a file path here is a link you can follow. Two things are not linkable and the entries say so rather than dressing it up. The runs/ directory is in .gitignore, so raw sweep artifacts are cited by path without a link; where the same figure survives into the published record, the entry cites data/runs.json instead, which is on this origin and is the file the board renders from. And two supporting repositories, mcp-tape and mcp-replay, are private, so their entries cite a commit hash, a path and a test name as text. The one publicly checkable artifact among them is mcp-tape 0.7.3 on npm, which is where the pairing fix shipped.

01

The first full pass scored nobody. Every server refused.

ON RECORD

What happened

The first leaderboard covered the whole verified roster and earned zero scores. It published 16 rows across 14 distinct public servers, two of them driven twice, and not one row carried a score field. The outcomes were 7 DEGENERATE, 8 INSUFFICIENT_SURFACE and 1 GATE_FAILED at the construct gate.

02

Those refusals were mostly our generator, not the servers.

CLOSED

What broke

Under the earlier generator a model with no server and no tools at all passed most of nearly every suite. The published no-tools rates were: astro 12 of 12, context7 10 of 10, cloudflare docs 2 of 2, coingecko 11 of 12, hugging face 11 of 12, svelte 10 of 12, better auth 8 of 9, microsoft learn 8 of 9, and aws knowledge 6 of 8. How it was caught

By turning the generator null-hard and re-running the roster. The earlier rows were never deleted, so the comparison exists. Every row on the board carries its generator version as a chip, and rows built by different generators are never read against each other.

03

A regex that does not compile in JavaScript destroyed half of every candidate generated after the first pass.

OPEN

What broke

Across the sixteen runs recorded as fitness-report-generator/2, 198 of 386 generated candidates were dropped with the rule invalid-check and the detail "regex does not compile". Every one of them was a tool_result_matches check. The generator instructions make that check kind required whenever the answer lives in a tool result, and never state the regex dialect or the JSON escaping the validator will apply. The validator then compiles with new RegExp(c.pattern) and drops on any failure. There is no repair pass for an invalid check; only an answer leak buys the one regeneration attempt.

What it caused

Three runs lost 24 of 24 candidates: microsoft learn, better auth, and the aws knowledge attempt now on the board. Three more kept 1 of 24: cloudflare docs, context7 and vercel docs. Astro kept 4 of 24. All seven of those runs are published right now as GATE_FAILED or INSUFFICIENT_SURFACE, which reads on the board as a statement about the server. Microsoft learn generated 9 usable tasks under the earlier generator and 0 under the null-hard one.

How it was caught

By totalling the drop counts across the sweep after the roster was rebuilt. Those counts were already being serialised into every published run, which is the only reason the number is recoverable at all; the per candidate ledger behind them is not published, which is entry 17. It is still open: the prompt and the validator still disagree about the dialect, and nothing repairs an invalid check.

Evidence

  • file data/runs.json, sum gates.records[structural].detail.synthesis.dropsByRule["invalid-check"] over the sixteen the null-hard generator rows: 198, against 386 in the matching yield.candidates
  • source src/tasks/synthesize.ts lines 1198 to 1202, the instruction that requires the check and states no dialect
  • source src/tasks/synthesize.ts lines 1581 to 1584, the new RegExp compile and the drop
04

The answer-leak detector was blind to the wire shape, and published an empty leak list that looked clean.

CLOSED

What broke

The generation-time scan normalised task parameters with Object.entries() and kept only string, number and boolean values. On the wire, params is an array of {name, value} objects, so every value failed the type guard and the scan rendered the task template with no bindings at all. It was checking a template, not a prompt.

What it caused

All 180 first-pass candidates, 12 requested across each of 15 sweep runs, went unchecked. Every one of those runs recorded answer_leak ok: true with an empty leak list and no regeneration attempted, and all 16 published rows carried the same empty record. An empty leak list is indistinguishable from a clean bill of health, which is exactly what it looked like.

How it was caught

While rewriting synthesis for the the null-hard generator generator. It is documented in the source as a proven the earlier generator bug and pinned by two tests that assert the scan reads the rendered prompt and the wire shape.

Evidence

  • source src/tasks/synthesize.ts lines 1339 to 1351, the bug documented in the past tense
  • test test/synthesize.test.ts: "checks the RENDERED prompt, not the template, and reads the WIRE shape of params"
  • test test/synthesize.test.ts: "binds params from the wire shape and the legacy record shape identically"
  • file site/data/runs.json at 302a62e, all 16 rows carry the empty leak record
  • commit 2836d72, the fix
05

The null gate killed our own first pipeline fixture, correctly.

CAUGHT EARLY

What broke

The first integration fixture built its task suite on a bare "was the tool called" predicate. A stubbed-empty null model satisfies that by definition, so the null baseline killed the fixture as degenerate. The gate was right and the fixture was wrong.

What it caused

Nothing published, because it happened while the pipeline was being written. It is in the record because it is the cheapest available proof that the gate bites, and because the rule it produced now runs in production: a bare tool_called check is rejected at generation with reason check-too-permissive, allowed only on a declared error-path probe. Three published runs, coingecko, convex and hugging face, each record one such drop.

  • source src/tasks/synthesize.ts lines 1564 to 1570, the production rule

06

The paid construct gate is a tautology by construction.

CAUGHT EARLY

What breaks, structurally

The reference agent is handed the answer key. For a substring or regex check, that means the check reads final text the agent could have produced from the key alone, with zero tool calls, against a server that is entirely dead. Left alone, the first gate that costs real money would pass on nothing at all.

What it would have caused

A paid gate that certifies a suite as constructible against a server that never answered. It never happened. The reached-through-server requirement is present in the initial commit, and the first scored row appears seven commits later, so no published row was ever produced by an unguarded construct gate. The gate is stated as a tautology-by-construction in the methods text of every report rather than presented as sound.

Evidence

  • source src/cli.ts lines 1490 to 1500: reachedThroughServer requires an ok tool call to an expected tool, and the verdict is run.outcome.success && reachedThroughServer
  • commit c5743b6, the initial commit, already carries the guard at src/cli.ts lines 645 to 654; src/gates/construct.ts has only ever had this one commit
  • test test/pipeline.test.ts: "refuses at the construct gate when the reference pass never reached the server", driven by a client that quotes the answer key back
07

One confirmation cleared every later destructive call in the task, whatever tool it named.

CAUGHT EARLY

What broke

Confirmation evidence was keyed by task alone and tool-agnostically. A single clarification round on any tool in a task marked every later destructive call in that task as confirmed.

What it would have caused

A recorded, unconfirmed money transfer publishing as "0 destructive calls with no confirmation in front of them". That is the safety number on this board, and it would have read clean while the tape showed the opposite. No scored row was ever produced under the broken keying: it was caught and pinned in the initial build commit.

How it was fixed

Evidence is now keyed three ways, by task and tool together, by tool, and by an explicit unattributed bucket for evidence that names no tool. Clearing a call requires evidence that names the same tool and lands before the call executes.

Evidence

  • source src/score/metrics.ts lines 267 to 307, the defect in the past tense and the ConfirmationEvidence shape that replaced it
  • test test/score.test.ts: "does not let a confirmation about one tool clear a destructive call to another"
  • test test/score.test.ts: "accepts a same-tool confirmation event that lands before the call"
08

An extension batch quietly deleted the tasks that would have refused the registered suite.

CAUGHT EARLY

What broke

The same predicate ran on registered suites and on bought extension batches with opposite consequences. A batch task that leaked its answer key, or shipped an unbound placeholder to an agent, was counted into a dropped tally and deleted without a word. The identical defect refused one run and silently shrank another, and the batch bought specifically to settle a verdict was the one place the defect could hide.

What it would have caused

Sampling bias pointing in exactly one direction: toward resolving the gate. The rule now splits by severity. An answer leak or a structural property violation inside a batch refuses the whole run, and a refused batch is voided whole. An ordinary admission failure, a duplicate or a null-screen deletion is dropped and said out loud.

Worth stating plainly

The asymmetry was corrected inside the same commit that introduced the extension loop, and when that loop first fired in production, on the hugging face null-hard run, both batches recorded zero drops of any kind. So the fix has never been exercised outside its tests.

Evidence

  • source src/cli.ts lines 522 to 549, the old behaviour in the past tense and the refuse-or-drop rule that replaced it
  • test test/extension.test.ts: "REFUSES on an answer key inside a batch, exactly as the registered suite does"; "REFUSES on a structural property violated inside a batch"; "DROPS an ordinary admission failure, and says so rather than refusing"; "REFUSES the run when a bought batch violates the structural property"
  • commit 95706f8, the commit that introduced the loop and the correction together
09

Nothing stopped a bought batch from restating a task already in the pool.

CAUGHT EARLY

What broke

Extension task ids carry an e<index>- prefix, which makes every batch id unique. Precisely because the prefix guarantees uniqueness, the id is useless as a duplicate test, and nothing else was testing for one.

What it would have caused

A restated task inflating pooled n with a correlated trial, which is the one thing pooling must not do. Deduplication now keys on task content, not on id.

Worth stating plainly

Same as the entry above: fixed inside the commit that introduced the loop, and the one production run that consumed extensions recorded duplicate drops of 0 in both batches. Pinned by tests, unexercised in the field.

Evidence

  • source src/cli.ts lines 585 to 594, and taskContentKey
  • test test/extension.test.ts: "drops a batch task that restates one already in the pool"; "dedupes inside one batch too, not only against the pool"; "keys task identity on content, never on id"; "drops a batch task that restates a pooled task, and still consumes the extension"
  • commit 95706f8, "Content level dedupe stops a restated task from inflating pooled n"

Published-number honesty: figures that were wrong, or would have been

10

"Total measured spend: $8.04" was not measured. $2.25 of it was a guess.

CLOSED

What broke

The first pass published a spend figure of $8.04 and called it measured. The ledger's fifteen entries sum to $8.0361, of which $5.7861 is runner spend priced from recorded tokens. The remaining $2.25 is fifteen copies of a flat $0.15 judge allowance, a constant in the sweep script that was never a measurement of anything.

What it caused

A published number understating real spend, wearing the word "measured". When judge spend was actually measured it came in at $0.421 on the first priced run. Recomputing the same fifteen runs at the replacement constant gives about $12.09, roughly half again as much as the figure that was published.

How it was caught and what changed

By measuring it. Judge usage is now read from the run record instead of assumed, and this is the concrete instance the floor labelling exists to prevent: a figure known to be incomplete is published as a floor with the reason it is one, and never as a total.

Evidence

  • source scripts/sweep-one.sh at 302a62e, line 18: OPUS_EST = 0.15 # synthesis allowance per run

11

The flat judge allowance was nearly three times too low, so every reported total was understated.

CLOSED

What broke

The spend ledger priced judge synthesis at a flat $0.15 per run. Measurement replaced it with $0.42, a factor of 2.8, and the replacement is itself labelled in the script as a guess rather than a measurement.

What it caused

Every total resting on the old constant was too small. The thirteen runs that now record real judge usage range from $0.2642 to $1.4495, with a median around $0.44, so the spread is far wider than any single constant can represent.

The ledger now reads run.judgeUsage.estCostUsd where the run recorded it and stamps the entry as measured. Where it did not, the figure is a floor, and the board carries that floor upward: if any run figure is a floor, the board total is a floor too.

12

A repair pass was counted as new candidates, inflating the denominator the structural gate tests.

CAUGHT EARLY

What broke

The generator counted rewrites as additional candidates: generated += rewrites.length. With 12 raw candidates and 4 rewrites the reported admission rate was 0.750 where the true rate was 1.000, and that inflated denominator went straight into the structural gate's 0.25 floor.

What it would have caused

False admission-rate refusals: runs refused for a generator failure the generator did not commit. It never reached a published number, and the reason is uncomfortable rather than reassuring. Because the answer-leak detector in entry 04 never fired, no regeneration was ever attempted, so no repair pass ever ran and the double count never had anything to double. One defect was masked by another.

Evidence

  • source src/tasks/synthesize.ts at c5743b6, line 1004: generated += rewrites.length
  • source src/tasks/synthesize.ts lines 437 to 447, the worked 12-and-4 example
  • source src/cli.ts lines 1249 to 1254, "would have refused runs the generator did not earn"

13

Per-tool failure classes were counted twice, so attribution would have read double.

CAUGHT EARLY

What broke

The runner reports a terminal failure class and the tool it is attributable to for every failed task. A class derived from the wire was then bumped a second time from the outcome, so a single failure was attributed twice to the same tool.

What it would have caused

Published per-tool attribution at twice the real failure count, which is the column a server author would act on. It was caught and pinned in the initial build commit, before any scored row existed. 6. What the numbers do not mean

Three readings the board does not support, stated before someone makes them.

Intervals that overlap are not a ranking

First-try success is drawn as a Wilson 95% interval on a shared axis. A row would only sit below another if that other interval lay entirely above it, and on the published runs no pair is separated that way. So the board prints no positions at all. Two rows at 12 of 12 and 9 of 12 at these sample sizes are not distinguishable, and reading them as first and second place is reading noise.

Runs under different generator versions or runner models are not comparable

Every row carries its task generator as a chip. A the earlier generator row and a the null-hard generator row of the same server are two different measurements, and entry 02 is exactly how far apart they can be: the same server, the same tools, a null model passing 10 of 12 under one generator and 0 of 12 under the next. The runner model is pinned into every score record for the same reason. Token accounting is not comparable across tokenizers, so two servers driven by different runner models are reported side by side and never read against each other.

The generation-time null screen adds a bias in one known direction and it is stated rather than buried: on a screened suite the run-time null baseline measures the noise floor of a suite that was already purged of the tasks that gate looks for, so it reads lower than it would on an unscreened suite. Every row prints which it is.

A refusal is not a verdict on the server unless the gate says so

DEGENERATE, INSUFFICIENT_SURFACE and a structural GATE_FAILED are statements about our own eval. They mean our generator did not produce a suite worth driving. Entries 02 and 03 are the proof that this distinction is not academic: fourteen currently published refusals across the two of them are our generator, published in the slot where a reader looks for a fact about the server. Seven are rows with no generator version recorded, seven are rows recorded as fitness-report-generator/2, and all fourteen are still on the board.

The one refusal that can carry a server finding is the construct gate, and only when the record reads it off the tape: tool calls recorded, calls returned as errors, requests with no matching response. When it says that, it says it from the counts. When it does not, it does not.

7. Cost honesty

Measured per phase and per model, published as a floor when anything is missing, and withheld entirely when nothing supports it.

Every run uses two models. The runner drives the server and its turns are on the agent tape, so its tokens are counted and priced from the record. The judge synthesises the task suite and produces the destructiveness signal before the drive begins, and it writes to neither tape. A total summed from the tapes alone is therefore the runner's spend, not the run's, and entry 10 is what happens when that difference is papered over with a constant.

Measured per phase and per model
Judge usage is read from the run's own record, per model, with calls, input tokens, output tokens and cache tokens broken out. Thirteen published runs carry it, ranging from $0.2642 to $1.4495 with a median around $0.44. Runner spend is priced from recorded tokens at the pinned model's price. Nothing is derived from a per-run assumption.
A floor is labelled a floor
A figure is called a total only when nothing known is missing from it. Every other figure is printed as at least, with the reason it is one, and the reasons come from the record: judge usage the harness marked partial, a judge model in the breakdown with no price on file, judge calls that returned no usage block, calls that threw before reporting any, and the same on the tape side. Each of those means dollars were spent that are not in the number. A floor printed as a total is a wrong figure wearing a right label.
A floor propagates upward
If any run figure on the board is a floor, the board figure is a floor. It is not averaged away and it is not rounded into confidence.
An unpriced model yields no number
Pricing fails closed. A model on a tape with no price on file produces no cost figure at all rather than a wrong one, and the record says why the figure is absent. Every new model needs an explicit price entry before its runs can carry dollars.
What is named without a number
Judge spend on runs that do not record it, the generation-time null screen calls that are written to neither plane, and any model on a tape with no price on file. Each is named on the board without a figure attached, because naming what sits outside a number is part of publishing the number.

Verify: judgeUsage on any row of data/runs.json, and the floor labelling pinned by four tests in test/site.test.js: "labels a partial judge block as a floor and says why", "labels each published run by what its own record supports, floor or total", "carries the floor up to the board figure whenever any run figure is one", and "states the spend as a floor and links to what sits outside it".
